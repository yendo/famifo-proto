# 日ごとの区切りを入れた一覧

## 解決する問題

一覧が全期間ひとかたまりで、写真と写真のあいだに一切の区切りがない。スクロールしていても、いま見ているのがいつの写真なのか分からない。

日付スクラバーは既にあるが、これは「ドラッグ中に年月ラベルが出る」もので、操作しなければ何も出ない。眺めているだけの利用者には現在位置の手がかりが無い。

実測（`~/Pictures`、4495枚、2009-04-06 〜 2026-02-08）:

| | 値 |
|---|---|
| 総枚数 | 4495 |
| 撮影日数 | 140日 |
| 月数 | 56か月 |
| 1日あたり | 最小1 / 中央値12 / p90 86 / p99 173 / 最大463 |
| 60枚を超える日 | 25日 |
| 1枚しかない日 | 28日 |

写真は日単位で強く固まっている。140日で4495枚、うち76日が11枚以上。フォルダ階層を無視したフラットな一覧でも、**日で切れば自然にイベント単位のかたまりになる**。

## 目標

- スクロール中、いま見ている写真がいつのものか、操作しなくても分かる
- 日ごとのかたまりが視覚的に区切られる
- 仮想スクロールの性質（任意の位置へ即座に飛べる、全体の高さが事前に確定する）を維持する

## 目標としないこと

- **見出しの上端吸着（sticky）** — レイアウト計算はそのまま使えるので、後から独立して足せる。今回は入れない
- **開いたまま新着を自動反映する** — 別機能。「既知の制約」に影響を記す
- 月単位・2段階（月の大見出し＋日の小見出し）の区切り — 日単位で足りる（下記）
- 検索、フォルダ階層のブラウジング（`2026-08-20-virtual-scroll-design.md` の決定を維持）

## 決めたこと

### 粒度は日

月単位も検討したが、1か月あたり平均80枚（7列で約12段）あり、区切りを入れても「ひとかたまり」感は半分しか解消しない。既存のスクラバーも月粒度なので、得られる情報が被っている。

### 少ない日は横に並べる

日単位で切ると、1枚しかない日が140日中28日（20%）できる。「見出し行＋写真1枚」の区画が並ぶと間延びする。

そこで、**その日が占める列数を `min(枚数, 列数)` とする**。1枚の日は1列、4枚の日は4列。1行に収まらない日だけが行を占有する。閾値も特例分岐もない一本の規則で、1枚の日の横並びはその帰結として自動的に得られる。

閾値を「1枚だけ」「列数の半分以下」に置く案も比較した。**3案とも実装は同一のアルゴリズムで、閾値の定数が違うだけ**なので、選択の基準は見た目だけになる。実測は次のとおり。

| | スマホ3列 総高 | 空セル | デスクトップ7列 総高 | 空セル | 横並びになる日 |
|---|---|---|---|---|---|
| 横並びなし | 100% | 158 | 100% | 524 | 0/140 |
| 1枚の日だけ | 98.9% | 113 | 97.6% | 412 | 28/140 |
| 列数の半分以下 | 98.9% | 113 | 96.0% | 342 | 28〜45/140 |
| **1行に収まる日すべて（採用）** | **98.6%** | **104** | **95.9%** | **335** | **39〜52/140** |

スクロール量はどの案でも1〜4%しか減らない。**横並びの価値はスクロール削減ではなく、寂しい区画をなくす見た目にある**。

### 日付ラベルは溢れない

タイル1列の幅は最狭でも約120px。

| ビューポート | 列数 | 1列の幅 |
|---|---|---|
| 375px (iPhone SE) | 3 | 119.7px |
| 390px | 3 | 124.7px |
| 430px | 3 | 138.0px |
| 768px (iPad 縦) | 4 | 187.0px |
| 1024px (iPad 横) | 6 | 166.0px |
| 1440px | 7 | 201.1px |

`2025年12月25日(木)` が約114px（font-size 12px 想定の見積り）で、最狭の1列にぎりぎり収まる。余裕が5%しかないので、**曜日を出すなら年を省く**。同じ年は年を省略する方式を採る。

## 覆す既存の決定

`docs/design.md` の次の決定を部分的に変更する。

**「バックエンド/フロントエンド境界: HTMLフラグメントパターン」のうち、カードと日付ラベルの markup をクライアント側に移す。**

どの日が横に並ぶかは列数、すなわち画面幅で決まる。列数を知っているのはブラウザだけなので、サーバーはレイアウト済みのHTMLを返せない。

代案として「列数をサーバーに送り、レイアウト済みHTMLを受け取る」を検討したが、採らない。クライアントは `#spacer` の高さと `scrollTop` → 表示範囲の対応を自分で計算しないと仮想スクロールが成立しないため、**レイアウト規則がGoとJSに二重実装される**。design.md がHTMLフラグメントパターンを選んだのは「二重実装を避ける」ためであり、守るべき対象が markup からレイアウトに移っただけで、原則自体は変わっていない。

「CSS Grid をやめてJSが全要素を絶対配置する」も検討したが、列数とブレークポイントをCSSからJSへ持ち込むことになり、`app.js` の `measure()` が明示的に避けた二重管理そのものになる。

移すのはカードの `<div>` と日付ラベルの `<div>` の2つだけで、タイルの markup（URL・alt・loading 属性）はGoテンプレートに残る。

## 設計

### データ層とAPI

`store.MonthOffsets` を `DayGroups` に置き換える。月は日から `d[:7]` で導出できるので、月専用の口は持たない。

```go
type DayGroup struct {
    Date  string // "2006-01-02"。ローカル時刻で切る
    Count int
}
func (s *Store) DayGroups(ctx context.Context) ([]DayGroup, error)
```

`MonthOffsets` の「SQLの `strftime` はUTCで月を切るので使わず、Go側で `time.Local` に変換する」という判断はそのまま引き継ぐ。日単位ではこの問題がより頻繁に効く。

**`/dates` エンドポイントは削除する。** 日ごとの表は「スクラバーのラベル用の飾り」から「これが無いと1枚も描けない必須データ」に変わるため、非同期取得のままでは初回表示が空白になる。サーバーが先頭の塊を埋めて返しているのと同じ理由で、日ごとの表も最初のHTMLに埋め込む。

```html
<script type="application/json" id="daygroups">[{"d":"2026-02-08","n":37},...]</script>
```

140日で約3.6KB。毎日撮る10年分（3650日）でも95KB程度で、ページ読み込み1回きりなので許容する。ラウンドトリップも1本減る。

**`/items` の各タイルに `data-date` を足す。** 日ごとの表と累積和があれば「通し番号 → 日付」は計算で引けるが、そうしない。

日ごとの表は初回HTMLの時点で固定されるので、開いたまま fsnotify が新しい写真を拾うと、表と実際の並びがずれる。並び順は `taken_at DESC` で新しい写真は先頭に入るため、全体が下にずれる。

ズレを検出して直すのではなく、**ズレても害がない形にする**。サーバーが日付を送れば、クライアントは予測ではなく事実からラベルを作れる。日ごとの表はレイアウト（総高とスクロール位置の対応）にだけ使う。

| | 表だけ持つ場合 | `data-date` を付ける場合 |
|---|---|---|
| 日付ラベル | 全部1つずつずれる | 常に正しい |
| スクロールバーの目盛り | ずれる | ずれる（数枚ぶん） |
| 直し方 | リロードが必要 | 実害がないので放置可 |

コストは1タイルあたり22バイト、60枚の塊で1.3KB。

### レイアウト計算

日ごとに1エントリの配列を、埋め込んだ表と列数から組み立てる。写真ごとではないので、枚数が増えても軽い。

```js
{ y,        // このグループの先頭のy
  start,    // 先頭写真の通し番号
  n,        // 枚数
  span,     // 占める列数 = min(n, cols)
  col,      // 行の何列目から始まるか（横並びのとき0以外）
  packed }  // span < cols か
```

`y` も `start` も単調増加なので、どちらでも二分探索できる。

貪欲詰め（`cols` が変わるたびに組み直す）:

```
残り列数 = 0
各グループ g について:
  span = min(g.n, cols)
  if span < cols かつ 残り列数 >= span:  いまの行に載せる
  elif span < cols:                     新しい行を開いて載せる（高さ labelH + gap + tileH）
  else:                                 行を閉じ、ラベル1本 + ceil(n/cols) 段のタイル行
```

引けるものは3つで、仮想スクロールに必要なものが揃う。

- **総高** → `#spacer` の高さ。現行の `ceil(total/cols) * rowH` を置き換える
- **`scrollTop` → 描く範囲** → `y` で二分探索。大きい日の途中に着地したときは、その日の中の何段目かを割り算で出し、`start + 段 * cols` から必要な段だけ切り出す
- **通し番号 → `y`** → `start` で二分探索。リサイズ時の位置復元とライトボックスが使う

#### 予測と実際を一致させる仕掛け

JSが計算した位置とブラウザが実際に置いた位置がズレると全体が崩れる。2つで担保する。

1. **CSS Grid の自動配置は、上の貪欲詰めと同じ規則そのもの**である。`dense` を付けない自動配置は「順に置き、入らなければ次の行へ、後戻りしない」。各日を `<div class="daycard" style="grid-column: span 4">` として順に流し込めば、ブラウザは定義上こちらと同じ答えを出す。JSが列位置を指定して回る必要はない
2. **タイルの実寸はCSSが決めたまま**にする。カードは外側グリッドの `span N`（= N列 + N-1個のgap）、内側は `repeat(N, 1fr)` に同じ gap。これで内側の1枚は外側の1列と一致する。列幅は現行どおり `getComputedStyle` から読み、ラベルの高さだけ `--label-h` としてCSSに1箇所定義してJSが読む

### 描画

塊のキャッシュを、現行のHTML文字列から**タイルごとの `{html, date}` の配列**に変える（取得時に1回だけパースする）。描画は、行の範囲から必要なタイルを切り出し、日付の変わり目でカードを開いて文字列を組み、`win.innerHTML` に入れる。再描画の抑止キーは現行の `塊番号:個数` から `先頭:末尾:列数` になる。

貼る単位は塊ではなく**行**になる。現行の「塊をまるごと貼って `gridColumnStart` でずれを補正する」細工は消える。大きい日の途中から貼るときは、ラベルなしでタイル行だけのカードを貼る。

CSSの追加はカードとラベルの2つ。

```css
:root { --label-h: 20px; }          /* JSが読む唯一の定義 */
.daycard  { display: grid; gap: var(--gap); }
.daylabel { grid-column: 1 / -1; height: var(--label-h); }
```

`span` と `grid-template-columns` はJSがインラインで書く。`repeat(var(--n), 1fr)` はCSSの仕様上使えないため、custom property には寄せられない。

### 既存機能への影響

**ライトボックス** — 現行は `tile.parentElement.querySelectorAll('.tile')` で窓枠内の位置を数えているが、タイルがカードの中に入るため `parentElement` がカードになり、その日の中での位置しか数えられなくなる。

位置を数えるのをやめ、**組み立て時に各タイルへ通し番号を直接書く**（`data-i`）。クリックはそれを読むだけになり、`famifo.pastedIndex()` のエクスポートごと消える。「窓枠内の位置 + 貼り付け先頭」という間接計算が無くなる。

**スクラバー** — 現行は `offset = frac × 総枚数` で月を引いているが、行の高さが不均一になった時点でこの比例関係は成立しない。`y = frac × maxScroll()` からレイアウトの二分探索で日を引き、その `d[:7]` を月として出す。ドラッグ中の表示は月のままとする（17年ぶんを一気にドラッグするため、日まで出すとちらつく）。`/dates` を削除するので、月の一覧は埋め込んだ表から導出する。

**リサイズ復元** — 考え方は現行のまま（先頭に見えていた写真の通し番号を覚えて復元する）で、復元先を「通し番号 → `y`」で引く。列数もタイル高も変わっていないときに何もしない早期リターンは残す。`ResizeObserver` は `#window` 自身の高さの変化でも発火するため、これが無いとスクロールのたびに組み直しになる。

**初回表示** — サーバーが返す先頭の塊はカードに組まれていない平らなタイル列なので、JSが組み直すまでの1フレームだけグループ分けされていない状態が見える。ここは現行のまま（サーバーが平らなタイルを返し、JSが引き取る）とする。JSが無効でも一覧が見えるという現在の性質を、1フレームのちらつきと引き換えに手放さない。

## テスト

### 削除するもの

- `TestGridAlignmentPastFirstChunk`（`internal/web/browser_test.go`）— 「塊の先頭が行頭でないと横にずれる」不具合を守るテスト。行単位で切り出して `data-i` を打つ設計では、この不具合が構造的に起きない。守る対象が消えたので削除する
- `TestMonthOffsetsMarksMonthBoundaries` / `TestMonthOffsetsEmptyStore` — `DayGroups` 版に置き換え
- `TestDatesReturnsMonthOffsets` / `TestDatesOnEmptyLibraryReturnsEmptyArray` — エンドポイントごと消えるため、「ページが日ごとの表を埋め込むこと」のテストに置き換え

### 必ず残すもの

- `TestMonthOffsetsUsesLocalTime` — `TestDayGroupsUsesLocalTime` として残す。「UTCで切ると月初・日初の未明の写真が前の期間に落ちる」という知見は、日単位ではより頻繁に効くため価値が上がる

### Go側に足すもの（常に走る）

- `DayGroups` の境界・並び順（新しい順）・空ライブラリ・ローカル時刻
- **`DayGroups` の枚数の合計が `Count()` と一致し、区切り位置が `ListRange` の並びと合うこと** — 表と実際の並びがズレると全体が崩れるため直接押さえる
- `/items` の各タイルに `data-date` が付き、値がローカル日付であること
- ギャラリーページが埋め込む表が valid な JSON で、`ListRange` の並びと整合すること

### ブラウザテスト

現行はテスト側が `floor(i / cols) * rowH` でレイアウトを再現して位置を出している。これは成立しなくなるため、`famifo` が公開する「通し番号 → `y`」を呼ぶ形に差し替える。**テストが実装のレイアウト規則を写経するのをやめる**ので、二重実装が1つ減る。

新規に足すもの:

- **JSが計算した各カードの `y` と `getBoundingClientRect()` の実測値が一致すること** — 今回いちばん壊れやすく、しかも壊れても静かに壊れる（写真が微妙に違う場所に出る）ため、正面から押さえる
- 少ない日が同じ行に横に並ぶこと
- 列数を超える日が行を占有すること
- ラベルが正しい日付であること

日ごとの枚数を作り分けられるようにフィクスチャを足す。

### レイアウト計算の単体テスト

貪欲詰めと二分探索は純粋関数だが、この repo にはJSを単体テストする手段が無い。**レイアウト関数を純粋な形で公開し、`chromedp` の `Evaluate` から表形式で叩く**。新しい依存はゼロで、既存のブラウザテストの仕組みに乗る。

`layout.js` に切り出して `node --test` で回す案も比較したが、「単一バイナリ・cgo不要」の方針に対して Node というツールチェーンが1本増えるため採らない。

制約として、これらは `//go:build browser` の下にあり `go test ./...` では走らない。`browser_test.go` に既に記されているとおり、テストが黙って走らないままCIが緑になるのは避けたい事象であり、この制約は意識的に受け入れるものとする。実行方法は `README.md` に記載済み。

## 既知の制約

- **大きい日はラベルを見失う** — 463枚の日は7列で67段（約13,000px）あり、その間ラベルは画面外に流れ去る。上端吸着を採らなかった帰結。レイアウト計算はそのまま使えるので、後から独立して足せる
- **開いたまま新着が入ると、スクロールバーの目盛りが数枚ぶんずれる** — 日付ラベルは `data-date` により常に正しい。リロードで直る。自動反映（軽い `/version` を数十秒ごとに叩き、変化していたら表と塊のキャッシュを捨てて再構築する）は別機能として後から足せる。再構築のコードは列数変更時の経路が既に持っている
- **同じ日が端末幅で違う見え方になる** — 5枚の日は7列のデスクトップでは横並びの一部、3列のスマホでは行を占有するブロックになる。`min(枚数, 列数)` という規則の帰結
