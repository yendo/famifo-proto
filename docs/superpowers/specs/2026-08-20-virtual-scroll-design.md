# 仮想スクロールによる一覧の再実装

## 解決する問題

4495枚のライブラリで、古い写真に事実上たどり着けない。

実測（`~/Pictures`、4495枚）:

- `IMG_1112.JPG`（撮影 2022-11-08）は新しい順で **1777番目**
- 1ページ60枚の無限スクロールでは **30ページ目**、到達に **29回の追加読み込み**
- 累計で1740枚のサムネイル（約50MB）を転送し、その分スクロール操作も必要

原因は仕様の組み合わせにある。フォルダ階層を無視したフラットな一覧、撮影日時順、無限スクロールのみ、という3つの決定が数千枚規模で噛み合っていない。数十枚なら問題にならなかった。

利用者の探し方は「特定の写真を検索する」ではなく「なんとなく古い写真を眺める」。したがって検索機能ではなく、**スクロールそのものを速くする**方向で解決する。

## 目標

- 全期間の任意の位置へ、連続的な操作で即座に移動できる
- 移動中も写真が流れて見える（行き先を指定して飛ぶ「ワープ」ではなく「早送り」）
- 現在位置の年月が常に分かる

参照する体験は Google フォト。挙動から見る限り、仮想スクロールを土台に日付スクラバーを重ねた構成になっている。

## 目標としないこと

- ファイル名・日付・フォルダによる**検索**（探し方の聞き取りで否定された）
- フォルダ階層のブラウジング（フラット表示の決定を維持する）
- 写真ごとに高さの異なるレイアウト（下記「成立条件」を壊す）

## 成立条件：タイルが正方形であること

仮想スクロールは全体の高さを事前に確定させる必要がある。現行のグリッドはタイルが `aspect-ratio: 1` の正方形なので、次で計算できる。

```
列数   = 画面幅から算出（既存CSSの規則と同一）
行数   = ceil(総枚数 / 列数)
全体高 = 行数 × タイル高（= タイル幅）
```

写真ごとに高さが変わるレイアウトを将来採用すると、この前提は崩れる。正方形タイルは Task 11 で `object-fit: cover` とともに決めたものだが、本設計はそれに依存する。

## 覆す既存の決定

`docs/design.md` の次の決定を変更する。

**「HTMLフラグメントパターン + htmx」のうち、htmx を一覧から外す。**

htmx が得意なのは「末尾が見えたら追記する」という宣言的な操作で、`hx-trigger="revealed"` がそのまま使えた。仮想スクロールは「スクロール位置から可視範囲を計算し、DOM を入れ替える」という命令的な処理が主体で、属性では表現できない。fetch の道具としてだけ残すことはできるが、`fetch()` を直接書くのと変わらない。

**HTMLフラグメントパターン自体は維持する。** サーバは引き続き HTML 断片を返す。この方式を選んだ理由は「タイルのマークアップを1箇所に置く」ことであり、htmx とは独立している。JSON を返すと `items.html` と `app.js` の両方に同じマークアップを持つことになり、片方だけ直したときに初回表示とスクロール後で見た目が食い違う、気づきにくいバグを生む。

htmx（`internal/web/static/htmx.min.js`）は一覧から使われなくなる。他に用途がなければ削除する。

## アーキテクチャ

### サーバ側

**1. 窓枠の取得** — `GET /items?offset=<n>&limit=<m>`

`store.ListRange(ctx, offset, limit int) ([]Photo, error)` を追加する。

```sql
SELECT ... FROM photos
ORDER BY taken_at DESC, id DESC
LIMIT ? OFFSET ?
```

既存のインデックス `idx_photos_order (taken_at DESC, id DESC)` が効く。数千行規模では `OFFSET` の線形コストは問題にならない。

返すのは `items.html` が描画する HTML 断片。ただしセンチネル（`hx-trigger` を持つ末尾要素）は不要になるため、テンプレートから外す。

**カーソル方式の `ListPage` は削除する。** 唯一の利用者である `handleGallery`／`handleItems` が `ListRange` に移行するため、残しても呼び出し元がなくなる。`store.Cursor` と `parseCursor`、`cursorView` も同時に不要になる。

**2. 初回ページ** — `GET /` は次を返す。

- 総枚数を `data-total` 属性として埋め込む（高さ計算に必要。専用リクエストを増やす理由はない）
- **先頭の1塊（120枚）のタイルを埋め込んだ状態で描画する**

初回だけ空の状態を描画して JS の取得を待つと、一瞬灰色の画面が出る。先頭の塊はサーバ側で埋めておき、クライアントは塊番号0を取得済みとしてキャッシュに載せた状態で開始する。`items.html` は初回ページとチャンク取得の両方で引き続き共用する。

**3. 日付インデックス** — `GET /dates`

```json
[{"m":"2026-08","o":0},{"m":"2026-07","o":37},{"m":"2025-10","o":142}]
```

月ごとの開始オフセット。スクラバーの吹き出しと目盛りの両方に使う。4495枚でも月数は数百程度で、数KBに収まる。

全件の日付を送る案（正確だが約50KB）、ドラッグ中に都度問い合わせる案（通信待ちで操作がカクつく）と比べ、月単位で目的を果たせる。

**4. サムネイル** — `GET /thumb/<id>` は変更しない。

### クライアント側

**DOM 構造**

```
#gallery（スクロール領域）
 └ #spacer      height = 行数 × タイル高   ← ブラウザのスクロールバーはこれを見る
    └ #window   position:absolute; transform: translateY(先頭行 × タイル高)
       └ 可視範囲のタイルのみ
```

スクロールのたびに `scrollTop / タイル高` で先頭行を求め、可視範囲＋前後の余白ぶんのタイルを `#window` に入れ替える。DOM 上のタイルは常に数十枚に保たれる。

**取得の単位**

固定サイズの塊（120枚）でキャッシュする。塊番号は `floor(offset / 120)`。可視範囲を覆う塊と、その前後1塊を先読みする。

**列数の再計算**

列数は画面幅から求め、リサイズと画面回転で再計算する。オフセットと行の対応はクライアントの責任で、サーバはオフセット範囲を返すだけ。この分離により、回転や画面分割に自然に追従する。

**日付スクラバー**

右端の縦バー。ドラッグ位置の割合からオフセットを求めて `scrollTo` する。`/dates` を二分探索して吹き出しに年月を表示し、年の境目に目盛りラベルを置く。

スマホでは常時表示は邪魔になるため、スクロール中のみ表示し、停止後しばらくで消す。

### ライトボックスの作り直し

現行の `app.js` は `#gallery` 内の `.tile` を全て集めて左右スワイプを実装している。仮想スクロールでは可視範囲しか DOM に存在しないため、**このままでは窓枠の端でスワイプが止まる**。

さらに、HTML 断片しか受け取らない構成では、クライアントは「1800番目の写真の URL」を知る手段を持たない。DOM から消えているためである。

**解決策：塊を受け取った時点で `data-full` を抽出して控える。**

```js
const tmp = document.createElement('div');
tmp.innerHTML = chunkHtml;
const urls = [...tmp.querySelectorAll('[data-full]')].map(a => a.dataset.full);
cache.set(chunkIndex, { html: chunkHtml, urls });
```

ライトボックスは DOM ではなく**全体の通し番号**で動くようになり、窓枠の外へもスワイプできる。未取得の塊に入った場合はその場で取得する。

JS は `data-full` を読むだけでタイルの構造には触れないため、マークアップの重複は発生しない。

## 灰色の箱が2種類あること

| 状況 | 見え方 | 解消 |
|---|---|---|
| 塊がまだ届いていない | 空の灰色タイル | 数百ミリ秒 |
| サムネイルが未生成 | プレースホルダ画像 | 背景生成が到達したとき（数分かかりうる） |

利用者から見て区別がつかない。まずは同じ見た目で出し、実際に使って気になるようであれば後者にラベルなどを足す。先回りして作り込まない。

## 背景サムネイル生成との関係

別途、次の設計が合意済みだが未実装である。

- スキャンは DB 登録のみ（4495枚で0.1秒）
- サムネイルは背景ワーカーが**撮影日時の新しい順**に生成
- 未生成時はプレースホルダを返す

**本設計はこれと独立に実装でき、順序はどちらが先でもよい。** 現行コードはスキャン時に全サムネイルを生成する（4495枚で43分）ため、スキャン完了後であれば仮想スクロールで2022年へ飛んでもサムネイルは揃っている。

ただし両方を実装した場合、**背景生成の順序を見直す必要がある**。新しい順に生成していると、2022年へ飛んだ利用者は背景ワーカーがそこへ到達するまで（現行速度で約17分）プレースホルダを見続ける。仮想スクロールで任意の位置へ飛べるようになる以上、**表示中の範囲を優先して生成する**仕組みが要る。これは本設計のスコープ外とし、背景生成を実装する際に扱う。

## エラー処理

- **塊の取得に失敗**: その範囲は灰色のまま残し、次回スクロールで再試行する。一覧全体は壊さない
- **`/dates` の取得に失敗**: スクラバーは目盛りと吹き出しなしで動作する（位置の指定は引き続き可能）
- **総数が 0**: スペーサ高は 0、スクラバーは非表示

既存方針との一貫性を保つ。個々の失敗で全体を止めない。

## テスト方針

**サーバ側**（Go のテストで検証できる範囲）

- `ListRange` のオフセット境界: 先頭、末尾、範囲外、`limit` が残数を超える場合
- `ListRange` と `ListPage` が同じ並び順を返すこと（移行の正しさ）
- `/items?offset=&limit=` が断片のみを返し、`<html>` を含まないこと
- `/dates` が月ごとの開始オフセットを降順で返すこと、境界の月が正しいこと
- 不正なオフセット（負数、非数値）が 400 を返すこと

**クライアント側**（ブラウザ不在のため限定的）

Task 11 と同様、静的アセットが配信されることと、JS が依存するフックがテンプレート側に存在することを文字列で確認する。仮想スクロールの挙動そのもの（行計算、キャッシュ、スワイプ）は Go のテストでは検証できない。実機での手動確認を実装計画の最終タスクに含める。

## 実装後に手で確認すること

1. 4495枚のライブラリでスクロールバーが全期間を表していること
2. スクラバーをドラッグして 2022年へ移動し、`IMG_1112.JPG` 付近に到達できること
3. 移動中に年月の吹き出しが追従すること
4. ライトボックスを開き、窓枠の境界を越えて左右スワイプできること
5. 画面を回転させても位置が保たれること
6. スマホ実機で操作が引っかからないこと
