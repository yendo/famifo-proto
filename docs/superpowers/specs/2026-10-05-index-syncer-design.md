# スキャンと監視を1本のループにまとめる

## 経緯

2026-10-05 に `internal/index` の indexer・scan・watch をレビューし、設計上の問題を
4件、実装の不備を1件見つけた。いずれも 2026-09-07 の監査メモ
（`docs/superpowers/plans/2026-09-07-index-remaining-issues.md`）には無い。

| # | 問題 | 種別 |
|---|---|---|
| 1 | ディレクトリを移動すると、子ディレクトリの監視が古いパスのまま残る | 実装の不備 |
| 2 | ルートそのものが消えたとき、監視側に保護が無い | 設計 |
| 3 | 監視の集合を回復する経路が無い | 設計 |
| 4 | 長いスキャンの間、監視の取り込みが止まる | 設計 |
| 5 | 同じパスの取り込みに、入口をまたいだ排他が無い | 設計 |

設計の4件は根が同じである。今の役割は入口ごとに割られていて、`Scanner` と
`Watcher` がそれぞれ判断を持ち、`Indexer` は1枚の適用と枠を持つ。だが4件はどれも
**入口をまたいで1つであるべき判断**で、その持ち主がいない。

- 2: ルートの扱いの方針が `scanPass.emptyRoots` にしかない
- 3: 監視の集合を正しく保つ持ち主がいない。スキャンは木を全部歩いているのに、
  その結果を監視に渡す経路がない
- 4: どちらを先に取り込むかを誰も決めておらず、チャネルの性質が決めている
- 5: パスごとの「今だれが取り込んでいるか」が `Watcher.inflight` にしかない

### 各問題の証拠

**1。** `watch.go` の `handleEvent` は、ディレクトリの Create を受けると `addTree` で
配下を `fsw.Add` し直す。fsnotify（v1.10.1）は監視を inode で持っており、
`inotify_add_watch` が既存の wd を返すと、古い path を持つ登録をそのまま返す
（`backend_inotify.go` の `register`）。移動したディレクトリ自身は IN_MOVE_SELF で
外れるが、その子は外れない。`album/sub` がある状態で `mv album album2` のあと
`album2/sub/x.jpg` を作ると、イベントは `CREATE "/album/sub/x.jpg"` で届くことを
実測で確認した。新しい写真は `indexFile` の Lstat が ENOENT で落ち、次のスキャンまで
載らない。ルートの外へ出したツリーも監視枠を食い続け、同名のディレクトリを作り直すと
古いパスと重なり、外での削除が実在する写真の行を消しうる。

**2。** ルートを `mv` すると、ルートの監視自身に IN_MOVE_SELF が届き、Rename として
`handleEvent` に来る。`removeTree(root)` がそのルートの行とサムネイルをすべて消す。
スキャンは同じ状況を「空に見えるルート」として配下の削除を見送る。

**3。** スキャンが戻すのはインデックスだけで、監視の集合は戻さない。キューが溢れた
間に作られたディレクトリ、`max_user_watches` を使い切って `Add` に失敗した
ディレクトリ、アンマウントされたルート（fsnotify は IN_UNMOUNT で黙って監視を外す）は、
二度と監視されない。以降の変更は定期スキャンを待つことになる。

**4。** `slots.take` はブロックする送信である。満杯のバッファ付きチャネルでは、空いた
枠はブロック中の送信側（スキャン）に直接渡る。tick ごとの `tryTake` は空きを見つけ
られない。DBを作り直した直後の初回スキャン（4,495枚で37分）の間、監視が出す取り込みは
1件も走らない。

**5。** スキャンと監視が版の違う同じ写真を同時に取り込むと、古い版のワーカーの
`sweep(id, keep)` が新しい版のサムネイルを消しうる。新しい版の `Upsert` が最後に
着くと、DBは新しい mtime でサムネイルが無い。スキャンは mtime の一致で Unchanged と
判定し、二度と直さない。窓は狭いが、起きると直らない。

## 守る不変条件

`2026-10-04-index-concurrency-roles-design.md` の6つを引き継ぐ。3と5は投入する入口が
2つあることを前提に書かれていたので、その前提が無くなった形に言い直す。10-04 では
3は「入口は自分が出したぶんだけ完了を待てる」、5は「どこかで取り込みが走っているかを
監視が聞ける」だった。どちらも、5の目的である幽霊行の回収をスキャンに頼るための
手段だった。

1. ループは、所要時間が写真の枚数やサイズに依存する仕事を自分では走らせない
2. 同時に取り込む枚数の上限は全体で1つ
3. 停止時に、走っている取り込みの完了を待つ
4. 走査には背圧がかかり、ループは待たない
5. 取り込み中に消えた写真の行を残さない
6. 完了通知を渡し終えてから枠を返す

## 目標

- 入口をまたぐ状態と方針の持ち主を1つにする
- 問題1〜5を解く
- 監査メモの課題2（ディレクトリの Create でループの中で木を歩く）を同じ仕組みで解く

## 目標としないこと

- 監査メモの課題6（停止が取り込みに引きずられる）
- 監視側の `removeTree` をループの外に出すこと
- キューが溢れている間に起きた移動による、古いパスの重なり。スキャンでの回復に任せる

## 設計

### 登場人物

| 型 | 公開 | 役 | 持つもの |
|---|---|---|---|
| `Indexer` | ○ | 1枚を同期的に適用する。並行について何も知らない | roots、store、thumbs、log |
| `Syncer` | ○ | ディスクとインデックスを同期させるループ。入口をまたぐ状態と方針の唯一の持ち主 | fsw、保留2列、`inflight`、workers、interval |
| 走査 | × | 部分木を1つ歩き、見つけたものをループへ送る。歩いたディレクトリに監視を張る | 歩いている間の帳簿 |

`Scanner` と `Watcher` は `Syncer` にまとまる。

消えるもの:

- `slots`、`startIndex` / `tryStartIndex` / `run`、`busy()`、`*sync.WaitGroup` の受け渡し。
  枠を共有する理由は「投入する入口が2つある」ことだった。投入するのがループ1つに
  なれば、同時に走る数はループが `len(inflight)` として自分で数える
- `kicks` / `ScanRequests`。溢れや取り込み中の削除への対応はループの中の判断になる

10-04 の spec は `Indexer` が枠を持つ理由を「包みが適用と枠の両方に触るから」とした。
包みがループに移るので、`Indexer` は適用だけに戻る。10-04 の spec の「将来これを崩す
条件」のうち「枠を取り込み以外の仕事にも通すとき」に当たる（削除の仕事も通す）。

### ループが受けるもの

| 入力 | 処理 |
|---|---|
| fsnotify のイベント | 帳簿づけ（後述） |
| fsnotify のエラー | 警告。`ErrEventOverflow` なら全体の走査を要求する |
| 走査からの仕事 | 取り込みはスキャン側の保留に、部分木の走査からのものは監視側の保留に積む。削除はスキャン側の保留に積む |
| 走査の終わり | その走査の集計を受け取る |
| ワーカーの結果 | `inflight` から外し、墓標を処理し、次を渡す |
| tick | debounce を過ぎたものを渡せる状態にし、次を渡す |
| 間隔のタイマー | 全体の走査を要求する |
| `Scan` の呼び出し | 全体の走査を要求し、その Stats を返す相手として控える |
| ctx の終了 | 走査を止め、ワーカーの完了を待って戻る |

全体の走査の要求は、走っていなければ始め、走っていれば「終わったらもう1回」の印を
立てる。印は1つにまとまる（今の `kicks` の容量1と同じ意味）。

### 保留と渡し方

保留は2列ある。

- 監視側: パス → 最後にイベントを受けた時刻。debounce を過ぎたものが渡せる
- スキャン側: 仕事（取り込みか削除か、パス）の列。すぐ渡せる

`len(inflight) < workers` の間、監視側の渡せるものを先に、スキャン側を後に、
1件ずつワーカーの goroutine に渡す（問題4）。

既に `inflight` にあるパスは渡さず、保留に残したまま次の候補へ進む。完了を受けた
あとの渡し方で改めて候補になる（問題5）。同じパスが同時に2本走ることは無い。今の
`Watcher.flush` が取り込み中のパスを保留に残すのと同じ扱いを、両方の列に広げる。

取り込み中に届いた Write は監視側の保留の時刻を更新するだけなので、完了後に
debounce を過ぎてからもう一度取り込まれる。再取り込みの印を別に持つ必要はない。

ワーカーは仕事を1つ実行し、結果を容量 workers の結果チャネルへ送って終わる。
`inflight` から外すのはループが結果を受けたときなので、通知を渡し終える前に次が
走り出すことはない（不変条件6）。

### 背圧

走査の goroutine からの送信は、行き先の保留に空きがあるときだけ受ける（空きが無い
間は select からその case を外す）。ループはブロックせず、走査だけが待たされる
（不変条件4）。全体の走査と部分木の走査はチャネルを分け、上限も別に持つ。

| 走査 | 行き先 | 上限 | 理由 |
|---|---|---|---|
| 全体 | スキャン側の保留 | workers 件 | すぐ渡せるので、ワーカーが空いた瞬間に次があれば足りる |
| 部分木 | 監視側の保留 | 1,024件（`maxWalkBacklog`） | debounce の2秒を待ってから渡すので、上限がそのまま「2秒あたりに流せる件数」になる。512件/秒は取り込みの速さ（1枚で数百ミリ秒 × workers）より十分大きい |

部分木の上限は、監視側の保留の件数のうち部分木の走査が積んだぶんで数える。
fsnotify のイベントが積むぶんは数えない。イベントは読まないと取りこぼすので、
上限で止めることができない。これにより、今の「`pending` に上限が無い」は、
巨大なディレクトリを持ち込んだ場合については解消する。

### 走査

全体の走査と部分木の走査は同じ仕組みで、違いは2つだけである。

| | 全体 | 部分木 |
|---|---|---|
| 起点 | 各ルート | ディレクトリの Create を受けたパス |
| 見つけた取り込みの行き先 | スキャン側の保留 | 監視側の保留（debounce 付き。今の `enqueueTree` と同じ扱い） |
| 削除の判定 | する | しない |
| 同時に | 1本まで | いくつでも。全体の走査と並行してよい |

全体の走査は今の `scanPass` の帳簿をそのまま持つ。`AllPaths` を引き、見つけたパスを
消し込み、mtime が一致すれば Unchanged、ルートごとの発見数を数える。歩き終えたら、
見つからなかったパスのうち空のルート配下でないものを削除の仕事として送る。

どちらの走査も、歩いたディレクトリ（ルートを含む）すべてに `fsw.Add` を呼ぶ。
`Add` は冪等なので、溢れや監視枠の不足や再マウントで外れた監視は次の全体の走査で
張り直される（問題3）。`Add` の失敗はディレクトリごとに記録せず、走査1回につき
張れなかった数を1行にまとめて出す。監視枠が尽きた環境でスキャンのたびに数千行が
出るのを避けるため。

### スキャン1回の終わりと Stats

全体の走査が終わり、かつその走査が送った仕事がすべて戻った時点を、スキャン1回の
完了とする。ループはその走査が送った仕事の数を数えておく。

Stats は走査側の数とループ側の数を合わせて作る。完了したら結果をログに出し、
控えてある `Scan` の呼び出し元に返す。

| 出来事 | 数える先 |
|---|---|
| mtime が一致した（走査側） | Unchanged |
| 走査中に読めなかった、stat できなかった（走査側） | Skipped |
| 取り込みが成功した | Indexed |
| 取り込みが失敗した | Skipped |
| 取り込みが ctx の終了で中断した | どこにも数えない（今と同じ） |
| 取り込み中に墓標が立った | どこにも数えない。行は取り消しており、消したのはスキャンではないので Removed でもない |
| 削除の仕事で行を消した | Removed |
| 削除の仕事の前の Lstat でファイルがあった | どこにも数えない |
| 削除の仕事が失敗した | どこにも数えない。警告を出す（今の purge と同じ） |

スキャン側の保留にあるうちに監視の Remove で捨てられた仕事も、どこにも数えない。
そのぶんはループが「送った仕事の数」から引き、スキャンの完了の判定がそれを待たない
ようにする。

### 削除の仕事

スキャン側の保留に積まれた削除は、取り込みと同じくワーカーで走る。数千件を消すことが
あり、ループの中では走らせられない（不変条件1）。

ワーカーは消す前にそのパスを Lstat し、ファイルがあれば消さずに戻る。走査の後で
作り直されたファイルの行を消さないため。確かめてから消すまでの間に作られた場合は、
その Create が監視側の保留に入り、排他により削除の完了後に取り込まれるので行は戻る。

削除の仕事も `inflight` に入る。

### 監視の Remove / Rename（パス P）

1. P がルートそのものなら何も消さない。警告し、全体の走査を要求する（問題2）。
   スキャン側の `emptyRoots` の保護がそのまま効く。監視はその走査が張り直す
2. それ以外なら:
   1. 両方の保留から P 配下を捨てる
   2. `inflight` のうち P 配下に墓標（`removed`）を立てる。入口によらず立つので、
      今の `busy()` によるスキャンの前倒しは要らない（不変条件5）
   3. `removeFile(P)` と `removeTree(P)` をループの中で呼ぶ（今と同じ）
   4. `fsw.WatchList()` のうち P 配下を `fsw.Remove` する（問題1）。既に外れていれば
      無視する

墓標の付いた仕事の完了を受けたら、取り込みなら `removeFile` で行を取り消す（今と同じ）。

### 監視の Create / Write

- ファイル: 対象の拡張子なら監視側の保留に積む（今と同じ）
- ディレクトリ: 部分木の走査を始める。ループの中では歩かない（監査メモの課題2）

### ループの状態を持つ型

ループが受ける入力は9種類あり、状態（保留2列、`inflight` と墓標、スキャン1回の
進み具合）を select の中に直接書くと、1つの関数がすべての判断を抱える。状態は
goroutine を持たない非公開の型 `syncState` に切り出し、ループは入力を受けて
そのメソッドを呼び、返ってきた指示（どの仕事をワーカーに渡すか、どの行を取り消すか、
スキャンが完了したか）を実行するだけにする。

```go
type syncState struct {
	workers  int
	watched  map[string]time.Time // 監視側の保留
	scanned  []task               // スキャン側の保留
	inflight map[string]*running  // 取り込み中・削除中のパスと墓標
	scan     *scanProgress        // 走っている全体の走査。無ければ nil
	...
}
```

`syncState` はチャネルにも fsnotify にも触らない。ファイルシステムとDBに触るのは
ワーカーと走査とループで、`syncState` は「次に何をするか」を決めるだけである。

テストは公開APIだけで書く方針なので、`syncState` を直接テストすることはしない。
切り出しは select を薄く保ち、判断を1箇所に読める形で並べるためのものである。
振る舞いは `Syncer` を通したテストで確かめる。

### 停止

走査は ctx で止まる。ループはワーカーの完了を待ってから戻る。待ち方は今と同じで、
課題6はこの設計の範囲外。

## 公開API

```go
func New(roots []string, st *store.Store, thumbs *thumb.Provider, log *slog.Logger) *Indexer
func NewSyncer(ix *Indexer, workers int, interval time.Duration, log *slog.Logger) (*Syncer, error)
func (s *Syncer) Run(ctx context.Context) error
func (s *Syncer) Scan(ctx context.Context) (Stats, error)
func (s *Syncer) Close() error
type Stats struct{ Indexed, Unchanged, Removed, Skipped int }
```

- `workers` は `Indexer` から `NewSyncer` に移る。1未満なら panic する扱いもそのまま移る
- `NewSyncer` は戻る前にルートへ監視を張る。「監視を張る → スキャン」の順序を呼び出し側
  から保証するため（今の `NewWatcher` と同じ）
- `Run` は起動直後に1回目の全体の走査を始め、以後 interval ごとに繰り返す。interval は
  1回の完了から次の開始までの間隔（今と同じ）
- `Scan` は全体の走査を1回要求し、その Stats を待って返す。`Run` が動いていることが
  前提。走っている最中に呼ばれたら、その次の1回を待つ。呼んだ時点のディスクが反映される
  ことを保証するため

`main.go` は goroutine が2本から1本になる。

```go
ix := index.New(cfg.MediaDirs, st, thumbs, log)
syncer, err := index.NewSyncer(ix, cfg.ScanWorkers, cfg.ScanInterval, log)
if err != nil {
	return err
}
defer syncer.Close()
wg.Add(1)
go func() {
	defer wg.Done()
	if err := syncer.Run(ctx); err != nil {
		log.Error("syncer stopped", "err", err)
	}
}()
```

### テスト専用の口（`export_test.go`）

- `SetDebounce` と `InjectWatchError` は `Syncer` に移して残す
- `IndexFile` / `RemoveFile` / `RemoveTree` は残す
- `DisableAutoScan()` を足す。起動時と interval ごとの全体の走査を止める。`Scan` の
  Stats を見るテストで、`Run` が自分で始める1回と数が混ざらないようにするため

## 却下した案

### 3者を保ち、`Indexer` に共有状態を足す

パスごとの排他（mutex で守る map）と優先度付きの枠を `Indexer` に足し、ルートの方針を
`Indexer` の関数にし、スキャンが見つけたディレクトリをチャネルで `Watcher` へ渡す。
墓標まで `Indexer` に持たせれば、状態が割れることは避けられる。`Scan` を単独で同期的に
呼べる形も残る。

それでも採らない。`Indexer` に置く状態（パスごとの取り込み中と墓標、優先度付きの枠）は
採った案のループが持つものと中身が同じで、違いは置き場所だけである。この案ではそれを
mutex の下に置き、ワーカー・監視ループ・スキャンの3方向から触らせる。完了時に墓標を
見て取り消す処理をワーカーの上でロックを取得しながら行い、そこに優先度付きの枠の待ちが
絡む。加えて、監視の集合を回復するためにスキャンから `Watcher` へディレクトリを渡す
経路が要り、入口どうしが結びつく。課題2も残る。

この案の利点は既存のテストをほぼそのまま使えることだが、書き直しの量は設計を選ぶ
理由にしない。

### 調停役を新設し、`Scanner` と `Watcher` は通知するだけにする

中身は採った案と同じで、登場人物が4つになり受け渡しが1段増える。監視ループは既に
ロックの無い唯一の書き手であり、別の型に分けて得るものが無い。

## 引き換えになるもの

- `Syncer` のループは今の `Watcher.Run` より多くの入力を持つ。状態は増えるが、
  すべて1つの goroutine の中にあり、ロックは要らない。判断は `syncState` に寄せ、
  select は受けて渡すだけにする
- `Scan` は `Run` が動いていないと使えない。テストは `Run` を起こしてから `Scan` を呼ぶ
- テスト専用の口が1つ増える（`DisableAutoScan`）

## テスト

既存のテストは `Scanner` / `Watcher` を `Syncer` に置き換える。前提が変わるもの:

- `ScanRequests` と `busy()` を前提にした4件（取り込み中の削除・アイドル時・溢れ・
  他のエラー）は、振る舞いそのものを見る形に書き直す。たとえば溢れなら、溢れのあと
  全体の走査が走り、取りこぼしたファイルが載ること
- `TestNewPanicsOnWorkersBelowOne` は `NewSyncer` の検査に移す
- `TestScanDoesNotWaitForTheWatchersIndexing` と `TestScannerRunIsBroughtForwardByARequest`
  は前提が無くなるので、意図に合う形に書き直すか消す

新しい振る舞いは TDD で、失敗するテストを先に書く。取り込みを止めておく必要があるものは
既存の `serveFifo` を使う。

| 問題 | テスト |
|---|---|
| 1 | `mv album album2` のあと `album2/sub` に置いたファイルが載る |
| 2・3 | ルートを rename しても行が消えない。戻したあとの全体の走査の後、ルートに置いたファイルが監視で載る |
| 4 | workers=1。スキャン側の取り込みを fifo で止め、監視側とスキャン側の保留を両方積む。止めていたものを放したあと、次に走るのが監視側のものである |
| 5 | スキャンが fifo で取り込み中のパスに監視の Write が来ても2本目が走らず、完了後にもう一度取り込まれる |
| 削除の仕事 | スキャンの purge より先に作り直されたファイルの行が残る |
| 課題2 | ディレクトリの Create を受けてもループが止まらない（部分木の走査中に別のファイルの取り込みが進む） |

`go test -race ./...` を通す。
