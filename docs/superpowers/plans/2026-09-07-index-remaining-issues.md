# internal/index に残る問題

2026-09-07 の監査結果。`33e554b feat: index photos in parallel while watching` の
直後の状態を対象とする。7件のうち6件は3つの根に集約される。個別の項目は
それぞれ単独で着手できるように書いてある。

## 経緯と、この文書が前提とする不変条件

`33e554b` の前は、fsnotify の追従が写真1枚の取り込み（`IndexFile`）を監視ループの
中で直列に実行していた。取り込みは原本のデコードと縮小を含み1枚で数百ミリ秒
かかるため、その間 `fsnotify.Events` を誰も読まない。fsnotify の Events は
無バッファなので、読み手が止まればカーネルの inotify キューが溜まり、
`max_queued_events`（既定16384）を超えると変更そのものを取りこぼす。

`33e554b` で入れた不変条件は次の1つである。

> **監視ループはイベントの受信と帳簿づけだけを行い、実行時間が写真の枚数や
> サイズに依存する仕事を自分では走らせない。**

これを担うのが `internal/index/executor.go` の `executor` である。

| 名前 | 場所 | 役割 |
|---|---|---|
| `executor` | `executor.go` | 取り込みの実行を1箇所に集める。同時実行の上限は `workers` |
| `submit` | `executor.go:28` | 持ち場が空くまで待つ。`Scan` 用（走査への背圧） |
| `trySubmit` | `executor.go:36` | 待たずに false を返す。`Watcher` 用（待つと取りこぼす） |
| `scanner` | `scan.go` | 1回のスキャンが持ち回る帳簿。`Scan` の中だけで生きる |
| `Watcher` | `watch.go` | fsnotify の追従。`pending`（debounce）と `inflight` を持つ |

以下の問題は、この不変条件が**取り込みについてしか適用されていない**ことと、
設計に**部分木という単位が無い**こと、**整合性の回復が起動時の一度きり**である
ことから出ている。

---

## 根っこ

### 根1: 「ループは重い仕事をしない」が規約でしかない

`33e554b` が境界を作ったのは `IndexFile` についてだけである。`handle` から
呼べる操作の範囲は決めておらず、今の保証はコメント1つで成立している。同じ
`select` の中に残った重い操作（`filepath.WalkDir` と `DeleteByPathPrefix`）は
素通りした。`handle` に何か足せば黙って破れる。

該当: 課題2、課題3

### 根2: ディレクトリが単位として存在しない

すべてがパス1本で表されていて、部分木という単位がない。だから墓標は
`album/a.jpg` には立てられても `album` には立てられず（課題1）、ディレクトリの
イベントを個々のファイルに展開するために歩くしかなく（課題2）、部分木の削除が
前方一致の LIKE になる（課題3）。3つとも同じことの別々の症状である。

該当: 課題1、課題2、課題3

### 根3: 整合性の回復が起動時の一度きり

`Scan` は運転中に再実行できない。だから溢れを検知しても打つ手がなく（課題4）、
監視を張る前にスキャンするしかないので窓ができる（課題5）。運転中に `Scan` を
回せる設計にすれば、順序を「監視を張る → スキャン」に変えて窓が閉じ、溢れたら
再スキャンで回復できる。そのとき初めて `Scan` と `Watcher` が同時に走るので、
課題7の「`executor` を共有しているが同時実行の規約が無い」が問題として立つ。

該当: 課題4、課題5、課題7

## 課題1: ディレクトリ移動で幽霊行が残る

**根2。33e554b の非同期化で入った穴。着手に設計判断は要らない。**

### 症状

取り込み中の写真を含むディレクトリを移動すると、移動元のパスの行がDBに残る。
その行が指すファイルは存在しないので、一覧のタイルが404になる。次回起動の
`Scan` まで消えない。

### 証拠

`watch.go:132-136` の墓標は完全一致でしか立たない。

```go
if _, ok := w.inflight[ev.Name]; ok {
	w.inflight[ev.Name] = true
}
```

`mv album elsewhere` の場合、イベントの `ev.Name` は `album` だが、`inflight` に
あるのは `album/a.jpg` のような個別パスである。`RemoveTree`（`watch.go:140`）は
既にある行を消すが、取り込み中の写真はその後 `Upsert` されて残る。

同期実行だった `33e554b` 以前は、`handle` と取り込みが同じ goroutine にいたため
この順序は起こり得なかった。

### 直し方

`inflight` は最大でも `workers` 件なので、前方一致で回して墓標を立てるだけでよい。
`under(root, path)` が `scan.go:220` にある。

```go
for p := range w.inflight {
	if under(ev.Name, p) {
		w.inflight[p] = true
	}
}
```

`ev.Name` 自身が `inflight` にある場合（ファイル単体の移動）も `under` は true を
返すので、既存の完全一致の分岐は置き換えられる。

### 検証

`watch_test.go` の `TestWatcherLeavesNoRowForAPhotoMovedWhileBeingIndexed` が
ファイル単体の移動を見ている。同じ仕掛けでディレクトリ版を先に書く。

FIFO を「取り込みを止められる写真」として使う。`mkfifoPhoto` で作った
`album/a.heic` の取り込みを `waitForIndexing` で止め、`album` ごと `os.Rename`
してから `serveFifo` で通す。HEIC を使うのは、自前でサムネイルを作らないため
原本を1度しか開かず、EXIF の読み取りで止めれば取り込みの途中で動かせるからである。

期待: 移動先の行だけが残る。修正前は移動元の行も残って2件になる。

## 課題2: ディレクトリの Create がループ内でフルウォークを2回する

**根1。着手前に実測すること。**

### 症状

ディレクトリごと `mv` で持ち込むと、その配下を2回歩き切るまで
`fsnotify.Events` を読まない。歩いている間に起きた変更を取りこぼす。
`33e554b` で直したのとまったく同じ問題が、ディレクトリ経路にだけ残っている。

### 証拠

`watch.go:144-160`。`handle` は `select` の中（`watch.go:88`）から呼ばれる。

- `addTree`（`watch.go:157`、実体は `204-224`）— 配下の全ディレクトリに
  `fsw.Add`（inotify_add_watch）を発行する
- `enqueueTree`（`watch.go:160`、実体は `227-245`）— 配下の全ファイルを
  `WalkDir` で舐めて `pending` に積む

### 直し方の候補

`addTree` の歩き自体は避けられない。inotify は再帰監視をせず、1ディレクトリ=1枠を
要求するため、監視を張るには降りるしかない。避けられるのは「ループの中で歩く
こと」だけである。

決めるべきは逃がし先である。`executor` は `IndexFile` に固定されているので、
そのままでは使えない。取りうる形:

- `executor` を「1枚の取り込み」ではなく「1つの仕事」を受ける形に一般化する
- 監視ループに専用の walk ワーカーを1本足し、結果（追加すべき監視対象と
  積むべきパス）をチャネルでループに返す。完了通知は `w.done` と同じ作法になる

歩いている間に `pending` を直接触らせないこと。`pending` は Run の goroutine が
単独で所有しており、ロックが無い。

### 実測（着手前にやる）

`~/Pictures` の4,497枚（`measurement-corpus-in-pictures`）から、日付ごとの
サブディレクトリを1つ選んで監視下に `mv` し、`handle` の所要時間を測る。
停止時間がミリ秒台なら優先度は下がる。

## 課題3: 削除イベントごとに全表走査が走る

**根2。`store` の中で完結する。**

### 症状

削除・移動のイベント1件ごとに `photos` テーブルを全行舐める。しかもループの
中（`watch.go:140`）なので、その間イベントを読まない。

### 証拠

`store.go:125-135` の `DeleteByPathPrefix`。

```go
`DELETE FROM photos WHERE path LIKE ? ESCAPE '\' RETURNING `+selectCols
```

SQLite の LIKE 最適化は ESCAPE 句があると適用されない。実測（`EXPLAIN QUERY PLAN`）:

```
DELETE ... WHERE path LIKE '/a/b/%' ESCAPE '\'      -> SCAN photos
DELETE ... WHERE path LIKE '/a/b/%'                 -> SCAN photos
DELETE ... WHERE path >= '/a/b/' AND path < '/a/b0' -> SEARCH photos USING INDEX sqlite_autoindex_photos_2
```

`path` は `TEXT NOT NULL UNIQUE`（`store.go:28`）なので暗黙の索引がある。
使われていないだけである。4,497枚のDBで1,000枚消すと450万行ぶんの走査になる。

### 直し方

範囲比較に置き換える。前方一致は「`prefix` 以上、`prefix` の最後の1文字を
1つ進めた値より小」で表せる。LIKE のワイルドカードのエスケープ（`likeEscaper`）も
不要になる。

上限値の作り方に注意すること。パスの区切りは `/`（0x2F）なので `/a/b/` の上限は
`/a/b0`（0x30）になるが、区切り文字を固定で前提にせず、最後のバイトを進める形で
書くほうが安全である。

### 検証

兄弟ディレクトリを巻き込まないことの確認は既にある
（`store_test.go:115` の `TestDeleteByPathPrefixIsSeparatorTerminated`。`"album"` が
`"album2"` を消さない）。範囲比較でも同じ性質が要るので、緑のまま置き換える。

**`likeEscaper`（`store.go:131`）のエスケープにはテストが無い。** パスに `%` や
`_` を含むケースを先に足すこと。今の実装でも通るはずのテストであり、範囲比較に
変えるとエスケープ自体が不要になる。置き換えの前後で同じテストが緑であることが、
振る舞いを変えていない証拠になる。

## 課題4: 取りこぼしを検知しても何もしない

**根3。課題5と同時に設計すること。**

### 症状

inotify のキューが溢れると fsnotify は `ErrEventOverflow` を `Errors` に流すが、
警告を出すだけである。取りこぼしを知れる唯一の場所なのに、回復の引き金に
していない。落ちたぶんは次の起動まで反映されない。

### 証拠

`watch.go:90-94`。

```go
case err, ok := <-w.fsw.Errors:
	w.log.Warn("監視エラー", "err", err)
```

`fsnotify.ErrEventOverflow` は `fsnotify.go:270` で定義され、inotify の
バックエンドが `backend_inotify.go:398` で送出する。

### 直し方

`errors.Is(err, fsnotify.ErrEventOverflow)` を判定し、再スキャンを起こす。
ただし運転中に `Scan` を回せることが前提になるので、課題5・課題7と一体で設計する。

溢れは連続して来ることがある。1回の溢れごとにスキャンを起こすと重なるため、
「スキャンが要る」という印を立てて、走っていなければ始める形にする。

## 課題5: スキャン完了から監視開始までの窓

**根3。課題4と同時に設計すること。**

### 症状

起動時のスキャン中に起きた変更が落ちる。数千枚で数分かかる構成では無視できない。

### 証拠

`main.go:167` で `ix.Scan(ctx)` が終わってから、`main.go:177` で `NewWatcher`、
`183` で `Run`。監視対象の登録（`addRoots`）は `Run` の中（`watch.go:67`）なので、
実際に inotify が張られるのはさらに後である。

### 直し方

順序を逆にする。先に監視を張り、それからスキャンする。スキャン中に届いた
イベントは `pending` に積まれ、スキャンが終わってから流れる。

同じ写真をスキャンと監視の両方が取り込む可能性が出るが、`IndexFile` は
`Upsert` なので二重登録にはならない。無駄な再取り込みが増えるだけである。
気になるなら `Watcher` 側の `inflight` と同じ考え方で重複を落とせる。

`Scan` と `Watcher` が同時に走るので、課題7が同時に効いてくる。

## 課題6: 停止が取り込みに引きずられる

**独立。他のどれとも関係しない。**

### 症状

停止時、走っている取り込みの完了を待つ。NAS のマウントが固まっていると停止しない。

### 証拠

`watch.go:81` の `w.ix.executor.wait()`。待つ相手は `IndexFile`
（`indexer.go:58`）だが、`IndexFile` は `ctx` を `Upsert`（`indexer.go:81`）にしか
渡していない。`exif.Read`（`72`）と `thumbs.Prepare`（`78`）は `ctx` を見ない。

### 直し方

デコードは途中で止められないので、「1枚ぶん待つ」以上には縮まらない。
実際に決めるのは「固まったマウントを何秒待つか」である。`wait()` に上限を設け、
超えたら待つのをやめる形になる。待つのをやめた場合、ワーカーが後から
`Upsert` を呼ぶので、閉じた `store` への書き込みがエラーログに出ることを
許容するかどうかを決めること。

## 課題7: executor の共有に同時実行の規約が無い

**根3。課題5に着手すると顕在化する。**

### 症状

`Scan` と `Watcher` が同じ `executor` を共有している（`indexer.go` の
`ix.executor`）。今は `main.go` が順番に呼ぶので問題にならないが、それを保証して
いるのは呼び出し順だけである。同時に走ると `executor.wait()`（`executor.go:61`）が
相手の仕事の完了まで待つ。

### 直し方

課題5で順序を変えると同時実行が常態になるので、そのとき決める。
`wait()` が「自分が出した仕事だけ」を待つ形にするか、共有をやめて入口ごとに
`executor` を持つか（その場合 `workers` の意味が入口ごとになる）。

あわせて `pending` に上限が無いことも見ておく。`enqueueTree` が一度に全件積むため、
巨大なディレクトリを持ち込むとパスの数だけ増える。メモリだけの問題なので
緊急性は低い。
